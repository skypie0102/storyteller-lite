I would start straight with the refactor, not a broad legacy-code deletion.
The reason is practical: the old React/Tauri/Sigil-era implementation costs us essentially nothing in the final Lite runtime while it is excluded from the new Cargo workspace, but it is extremely valuable as a behavioral regression reference. Deleting it first would make migration harder without making the new app faster.
The two mockups are now stored in the branch as UI guides:
- docs/ui-guides/storyteller-lite-main-ui.webp
- docs/ui-guides/storyteller-lite-manual-allocation.webp
- docs/ui-guides/README.md
I also explicitly documented that the mockups are wide-window visual targets, not fixed canvases. The Slint implementation should reflow, hide secondary metadata when necessary, and use localized scrolling rather than absolute coordinates, so resizing the window won't mangle the UI.
For the actual code migration, I’d use this order:
1. Core job model first. Build the new Lite-native concepts in storyteller-core: Job, JobStatus, PipelineStage, structured progress, encoding settings, unmatched-audio policy, stage results, cancellation state, and queue transitions. This becomes the single source of truth for both the UI and processing backend.
2. Queue + scheduler next. Implement the auto-start queue and resource-aware scheduler independently of Slint. This is where we establish Waiting → Preparing → Processing → Needs Review → Processing → Complete/Failed, plus pause-after-current and cancellation.
3. Resumable stage system early. Before migrating expensive processing, establish the checkpoint/fingerprint architecture:
   Prepare → Analyze → Align → Review → Encode → Build → Validate.
   That way everything we port afterward automatically fits resumable processing instead of requiring a later redesign.
4. Structured progress events. Implement the exact data required by the UI mockup: one overall percentage, current activity text, current stage, chapter/track/audio position, elapsed time, ETA, speed, backend/model, match percentage, warnings, and cached/skipped stages. The UI should consume these events rather than parse console output.
5. Native EPUB foundation. Then extract the existing Rust EPUB integrity code into storyteller-epub and start building the single coherent EPUB model. This begins the real Sigil removal.
6. Audio/unmatched pipeline. Move silence detection and unmatched-audio inspection into Rust, add automatic edge trimming, Smart classification, lazy OCR, and then build the streamlined allocator around those APIs.
7. Persistent Whisper + processing optimization. Once the interfaces are clean, integrate the persistent whisper.cpp service, resource scheduler, minimal-transcode audio graph, caching, and low-copy staging.
8. Slint UI implementation. The UI can actually begin fairly early—after steps 1–4—because at that point it has a stable model to bind to. We can build the main mockup and allocator without wiring them directly to legacy subprocesses.
Then we delete legacy code incrementally. For example, once Slint Settings exists and the new settings model works, delete the corresponding React settings UI. Once native EPUB finishing passes regression tests, retire the Sigil normal path. Once Slint reaches full workflow coverage, remove React/Vite/Tauri as a unit.
The rule I'd use throughout the migration is:
Replace → regression-test → delete. Never delete → hope we remembered everything.

There are a few things we already know can be marked for eventual deletion without porting: word-level synchronization, Activity console UI, Runtime Health page, Process-now flow, worker/thread controls, engine/runtime path UI, standardize-EPUB toggle, CSS editor, old unmatched-audio mode selector, permanent OCR toggle, and the old full-complexity allocator presentation. But I would leave those source files intact until their surrounding legacy screens can be removed cleanly rather than surgically ripping individual pieces out now.
So the very next coding task I recommend is the new storyteller-core job + pipeline-state model. It is the foundation that lets virtually everything else become cleaner.

- Resource-aware scheduler
  - CPU, GPU-heavy, FFmpeg and I/O capacity are tracked independently.
  - GPU-heavy work can remain exclusive while lightweight preparation overlaps it.
  - The initial automatic profile for a 16-thread/32-GB/NVIDIA-class desktop derives 12 CPU units, 1 GPU-heavy slot, 6 FFmpeg slots and 2 I/O slots.
- Structured event journal
  - Stage changes, progress, metrics, warnings, cache reuse, review requests and failures.
  - Bounded at 256 entries by default.
  - This is the backend for the future Details view, not a return of the Activity console.
- New cancellation model
  - Shared cancellation token for an entire processing attempt.
  - Multiple simultaneous external child processes can be registered.
  - Fixes the old architecture's assumption that a job has only one active PID.
- Runtime coordinator
  - Centralizes resource leases, cancellation, child-process registration and job events.
  - FFmpeg/Whisper/alignment adapters will use this rather than manipulating UI/queue state themselves.
